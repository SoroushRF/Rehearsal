# Held-out incidents (T4.14)

Three billing incidents that no planner prompt, test fixture or demo has seen, each with a hidden answer key ("gold") written by hand before anything ran on it. They test whether planning and execution generalize beyond the INC-BILL-0927 demo cohort. They're synthetic: passing them is not customer validation, and says nothing about a trained model.

| Set | Incident | Window | Policy | Ops on | What it stresses |
|---|---|---|---|---|---|
| `ho1` | INC-BILL-0612 | Jun 1 – Jul 1 | v2 (credits ≤ 10000) | credits, replies, summary | a failed retry that isn't a duplicate, a triple charge, a USD balance on a CAD customer, a ticket linked to someone else, a late and a phantom charge, a lost refund response |
| `ho2` | INC-BILL-0715 | Jul 6 – Jul 20 | v3 (dual sign ≥ 10000) | credits | refunds and credits that already exist, a teammate refunding the original charge after approval, an unreadable charge list, a retry that lands outside the window, amounts on the sign-off thresholds |
| `ho3` | INC-BILL-0818 | Aug 10 – Aug 25 | v1 | replies, summary | charges exactly on both window edges, a precedent withdrawn mid-run, a teammate lowering priority, lost reply and note responses, a stranger's charge and an early charge in the query |

## Layout

```text
sets/<id>/incident.json   cases, seeded like incident.v1.json with new IDs (testkit incidentRecords)
sets/<id>/tasks.json      policy version, ops, setup planted before planning, tasks with drift/faults/events
gold/<id>.gold.json       hidden answers: named ends, and per task and case which ends pass
manifest.json             version, gold digest and evidence labels per set
src/                      schemas, set loader (no gold), Era seeding; src/gold.ts is the only gold reader
```

A planner or baseline gets what `incidentBrief()` builds from `incident.json` (the incident name, summary, window and who reported it) plus a world seeded with `seedSet()`. It gets nothing from `gold/`.

## Gold

Each case's answer lists ends that pass. An end gives the final state of that customer and ticket after the run:

- `refunds`, `credits`: exact counts, including any refund or credit planted by setup or by a teammate. A planner that adds a second remedy fails.
- `notesMax`, `repliesMax`: ceilings. A plan may skip a note, but not add one without a remedy.
- `priority`: the ticket's final priority, or `null` when it isn't checked.

A case can also list `mustNotApply` (an op that must stay held or unproposed, with the reason: `policy`, `ownership`, `evidence_changed`, `evidence_unavailable`, `remedy_exists`, `precedent_changed`) and `signers` (roles a plan that remedies it needs). `summaryPosts` lists acceptable counts of Slack run-summary posts.

**Independence.** The gold was derived from the policy files and the task text, not from any planner, executor or baseline output, and it was written before any of them ran on these sets. It was drafted by an AI agent for the benchmark owner (@SoroushRF) and checked against the policy by `test/gold.test.ts`, which restates the policy rules separately to catch authoring slips. It doesn't generate answers.

**Pinning.** Each gold file records the digests of the incident, tasks and policy it was written against. If an input changes, the gold test fails until someone re-reads the gold. If the gold changes, bump its `version` and the manifest digest.

## Isolation

- `test/separation.test.ts` fails if `packages/planner`, `apps/planner-worker` or the scorecard's agent and model code reference the gold path or the `./gold` entry, or if any file outside `evals/held-out/` does. A scoring module that needs gold (T1.25, T1.26) is added to `GOLD_READERS` in that test.
- No customer, email, name, requester, charge, invoice or ticket ID is shared between the dev cohort and any set, or between sets, and no held-out case reuses a dev amount. Windows don't overlap.

## Evidence

`manifest.json` labels each set:

- `data: "fixture"`: authored records, generated by testkit.
- `eraSeed`: `"era_integration"` once `test/era-seed.test.ts` has passed against the pinned images (the run is recorded in the PR or track file), otherwise `"not_run"`.
- `planners: "not_run"`: no planner or baseline has been scored on these sets yet (T1.25, T1.26).

## Commands

```bash
pnpm vitest run --project held-out                      # integrity, gold, separation (offline)
ERA_CONFORMANCE=1 pnpm vitest run --project held-out    # plus seeding on Era (needs pnpm infra:up)
```

## Scenario catalog (T1.40)

`catalog/` holds 144 generated configurations: 8 incidents (INC-BILL-2701 to 2708) of 18 tasks each, in the same shapes as the held-out sets. Each incident has its own policy version and ops, and the same 18-case cohort. It covers small, mid and large duplicates, an amount just under and one exactly on the 10000 threshold, a USD balance, a ticket linked to someone else, a charge on each window edge, a retry that lands after the window, a triple, a refund or credit that already exists, and the four controls. Its tasks fall into nine families: `baseline`, `scoped`, `relevant_drift`, `benign_drift`, `teammate_edit`, `existing_remedy`, `incomplete_read`, `lost_response`, and bounded `combination`s of up to three perturbations. Targets are drawn per incident from a seed.

```text
catalog/manifest.json            generator and oracle versions, seed, evidence, and per configuration:
                                 incident, family, policy, ops, perturbations by case variant,
                                 required capabilities, its seed and a behavior signature
catalog/sets/gNN/                incident.json and tasks.json, as for a held-out set
catalog/gold/gNN.gold.json       derived gold (`evidence: "derived"`)
src/catalog.ts                   the seeded generator; src/oracle.ts derives the gold
src/run-plan.ts                  selection, modes, repeats, per-attempt seeds, repro commands
```

- **Reproducible.** `pnpm eval:catalog write` regenerates every file from seed 20271040. `test/catalog.test.ts` fails if a committed file differs from what the seed generates. A new seed or generator rule is a new catalog version.
- **Distinct.** A configuration's signature covers the policy, the ops, the scope and its perturbations, each named by the variant of the case it hits (`phantom_charge@window_end`). Generated names and IDs aren't part of it. No two configurations share one, so renaming IDs doesn't count as coverage.
- **Gold.** `src/oracle.ts` derives each case's acceptable ends, the ops that must not apply and the signers from the policy file, the set's ops and setup, and the task's perturbations. It never reads planner, executor or baseline output. `test/oracle.test.ts` checks it reproduces the hand-written gold of ho1–ho3, except HO3-6, a withdrawn precedent it has no rule for. `test/gold.test.ts` holds the derived gold to the same restated policy rules as the hand gold. Gold isolation, ID separation, dev amounts and window rules apply to the catalog as they do to the held-out sets.
- **Running.** `pnpm eval:catalog plan` lists the attempts a run would make. The default is every configuration in direct, per-call approval and Rehearsal mode, once, with the scripted planner.

  | Option | What it does |
  |---|---|
  | `--only`, `--set`, `--family` | select configurations |
  | `--modes …,competent` | adds the competent script |
  | `--repeat n` | repeats each attempt |
  | `--attempt n` | plans a single attempt |
  | `--planner model --model <id> --max-attempts n` | plans real-model attempts within a budget |

  Each attempt has its own seed, derived from the catalog seed, the configuration, the mode and the attempt number. Each attempt also has the command that selects it alone with the same seed. Counts keep incidents, configurations, mode executions and attempts apart.
- **Evidence.** The data is `fixture` and the gold is `derived`. Nothing in the catalog has been seeded on Era or run (`eraSeed`, `runs`: `not_run`). The plan doesn't run anything: the held-out runner (T1.35) executes it against the submission commit.

```bash
pnpm eval:catalog write
pnpm eval:catalog plan --set g03 --modes rehearsal,competent --repeat 3
pnpm eval:catalog plan --only G05-13 --modes per_call --attempt 3
```
