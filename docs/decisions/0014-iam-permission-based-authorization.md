# 0014: IAM permission-based authorization (T4.15)

**Status:** proposed 2026-10-24 (skhdemo, T4). This changes API auth, approvals, and executor admission, so it needs a reviewer from T2 (@parsaabbasian) and from T3 (@ArtinMe) before it merges.

## Context

[0004](0004-clerk-roles-and-bearer-auth.md) maps a Clerk organization role onto Rehearsal roles in the API, and one grant that holds every role a plan names is enough. [0011](0011-two-distinct-approvers.md) asks for two people where policy says so, and still names the seats as roles. This record supersedes that role mapping and that single-grant rule, and amends 0011 so the two seats are permissions. Billing policy ([0010](0010-remedy-policy.md)) is unchanged. The bearer token from 0004 stays: the caller sends the session token, and a cookie is not a session. What moves is who checks it.

## Decision

1. **The app enforces. IAM decides.** API routes and executor admission ask IAM and stop when it does not allow. IAM is a generic service. It does not know refunds, Stripe, Zendesk, or dollar amounts. It evaluates one format: an action, a subject, and resource facts. Clerk is only identity: the user, the active organization, and one organization role. Versioned JSON in this repo holds the rules. IAM loads a named version itself. The caller cannot send the rule text.

2. **Names.** Permissions are `rehearsal:verb:object`. Roles are `owner`, `finance_lead`, `support_lead`, and `member`. There is no `admin`. The rule file maps Clerk roles one-to-one: `org:owner` → owner, `org:finance_lead` → finance_lead, `org:support_lead` → support_lead, `org:member` → member. Any other Clerk role, including `org:admin`, maps to nothing, and every rule denies it. The ladder lives in the rule file, not in Clerk. Do not create custom `rehearsal:*` permissions in Clerk. Clerk keeps only its built-in system permissions, and only `org:owner` holds the member-management ones. Owner is the creator role. Member is the default role for invites.

   Owner holds all 15. `member` holds `rehearsal:read:plan`, `rehearsal:read:run`, and `rehearsal:read:precedent`. `support_lead` holds those plus `rehearsal:rehearse:incident`, `rehearsal:revise:plan`, `rehearsal:approve:support_step`, `rehearsal:apply:plan`, `rehearsal:cancel:run`, and `rehearsal:revoke:own_grant`. `finance_lead` holds `support_lead`'s plus `rehearsal:approve:finance_step`, `rehearsal:revoke:any_grant`, `rehearsal:promote:precedent`, and `rehearsal:withdraw:precedent`. Owner alone also holds `rehearsal:invite:member` and `rehearsal:manage:role`. The precedent routes (`GET /api/precedents`, `POST /api/runs/:id/precedents`, `POST /api/precedents/:id/withdraw`, from decision 0012) use these, keeping today's behaviour (list for any member, promote and withdraw finance-only), with owner added.

3. **RBAC and ABAC.** IAM turns the Clerk role into that role's permissions from the rule file. `anyOf` means the subject holds at least one listed permission. `allOf` means the subject holds every permission in a list the app sends (a plan's `requiredPermissions`). The other checks compare attributes. Every person-facing rule includes `subject.orgId == resource.orgId`. `subject.*` comes from the Clerk token IAM verified. `resource.*` is read by the app from the stored database row, never from the URL, the body, or the caller's own organization. A wrong organization is answered 404, not 403.

4. **Facts.** The app never tells IAM who the person is. It sends the session token. IAM checks the token with Clerk. IAM has no database, so the app sends the facts IAM cannot look up: the item's organization; for approval, `requiredPermissions` and `dualRequired`; for revoke, whose grant it is; for `run:admit`, the saved grants. The app computes `requiredPermissions` and `dualRequired` from the billing policy (`scenarios/billing/policy.v*.json`). Dollars never reach IAM. A hash mismatch, a stale revision, and a policy violation stay in the app (409 / 422). Not found stays 404.

5. **Every in-org action a person takes goes through IAM.** No person-facing route keeps today's role checks. `CLERK_ROLES` in `apps/api/src/auth.ts` and the `grant.roles` admission check go away. Outside the rules, and not as the old role model: `GET /api/me` (signed in, active organization, returns identity and permissions, no rule); `GET /api/health`; the planner job routes and the tenant-token route (a machine secret, not a person). A test must fail if a registered person-facing route has no rule. That test is a later task; this decision requires it. IAM down, a timeout, a malformed answer, or an unknown rule version means deny, and nothing is written or sent.

6. **Apply and admit are different actions.** Clicking Apply (`POST /api/plans/:id/apply`) needs `rehearsal:apply:plan`. Starting a run is `run:admit`. It has no person and no Clerk call. It judges stored grants. When `dualRequired` is false, one live grant whose saved permissions cover `requiredPermissions` is enough. When `dualRequired` is true, two different users are required, one holding `rehearsal:approve:support_step` and one holding `rehearsal:approve:finance_step`. The API asks `run:admit` before queueing. The executor asks again before sending, and that answer is authoritative. A grant counts only when the organization, plan hash, and revision match, `revokedAt` is empty, and now is between `grantedAt` and `expiresAt`.

7. **Grants remember the permissions, not a later file.** A grant stores the permissions the approver held and the rule id and version. A later rule file does not rewrite an old grant. Old rows that only have `roles` are a migration question for the implementation tasks. They must not be treated as a silent allow.

8. **IAM is a separate service, called over mTLS.** It is not an in-process library. Only the API and the executor may call it. IAM presents a server certificate and accepts only client certificates it trusts: one for the API, one for the executor. The browser, the planner, and anyone else have no certificate and are refused before a question is read. Plain TLS is not enough, because it does not limit who can connect. Certificates never go to the browser. The Clerk secret stays in IAM. mTLS stops an outsider swapping facts on the wire. It does not help if the API process itself is compromised. The API and the executor act only when the decision names the same action and the same facts they sent.

9. **Rules and membership.** Changing a rule without a new kind of check is a new version of the JSON file, reviewed in a PR. IAM's code changes only when a new operator is needed. Inviting members and changing roles go through our API (`POST /api/members/invitations`, `PATCH /api/members/:userId/role`), which asks IAM and then calls Clerk. Only roles in the rule file can be assigned.

## Consequences

- Cancel, revisions, and the Apply click require a permission. Today any signed-in member can do them. Revoking one's own grant needs `rehearsal:revoke:own_grant`. Revoking anyone's needs `rehearsal:revoke:any_grant`. Today any approver can revoke any grant. Reads require `rehearsal:read:plan` or `rehearsal:read:run`. `org:admin` is not a Rehearsal role. `org:owner` is new and holds every permission. One owner still fills only one seat of a two-person approval.
- T4.15–T4.26, issues [#220](https://github.com/SoroushRF/Rehearsal/issues/220) through [#231](https://github.com/SoroushRF/Rehearsal/issues/231), are the implementation: this record, the contracts, rule file v1, the pure engine, the IAM service, API enforcement, grants that store permissions, executor `run:admit`, invites and role changes, the web UI, Clerk configuration, and an end-to-end acceptance.
- Cross-track: T2 paths (API auth, approvals, web, Clerk) and T3 paths (executor admission, db). Contracts, credential handling, and executor admission need a reviewer from another track.
