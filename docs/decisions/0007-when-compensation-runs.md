# 0007: When compensation runs (T4.4)

**Status:** proposed 2026-10-22 (T4). Please raise objections in team chat or on the PR.

## Context

The build plan says not to roll back every customer because one branch failed, and that compensation only writes owned fields back if they still hold our value. It doesn't say what counts as "failed", or whether a held step triggers it.

## Decision

1. **Trigger.** After the steps of a run, a case is compensated if one of its steps was definitely refused: a `rejected` receipt with a 4xx status other than 429. A 429 or a 5xx may be sent again by a later run, so it isn't final.
2. **Not a trigger.** A `held`, `unknown_outcome` or `skipped_dependency` step. A held case is waiting for a person, and an unknown one may have applied.
3. **Scope.** Only that case's confirmed `zendesk.ticket.patchFields` actions marked `conditional_reversible`. Refunds and notes are never undone, and other cases are untouched.
4. **Per field.** Re-read the ticket after capturing its stamp. A field that still holds our value gets its before value back through a stamp-guarded patch, journaled before dispatch. A field someone else changed is kept and gives `compensation_conflict`. Patches in one case are undone latest first, so a chain of writes to one field (normal → high → urgent) returns to the earliest before value instead of treating the later write as a teammate edit. An older patch records nothing while a later undo of the same field is still unresolved, so a lost response can be read before that value is overwritten. A hold with no dispatched attempt is not an unresolved undo, so it does not block the older patch. A send counts as dispatched when its operation key has an attempt under any revision, not only the current plan hash. A field counts as restored when the journaled undo request wrote it back to its before value, including after a lost response is reconciled by a read. A later undo that settled without restoring one field does not block a field it did restore. A field it left conflicted is not undone through the earlier patch, so a current value equal to the earlier write is kept. A 409 on the undo only means the ticket moved, possibly in another field, so compensation re-reads and decides again, up to three rounds; if it is still changing, the patch is held. A field that has to be undone by hand makes the outcome `held` even when another field is a conflict. A later round that finds nothing left to send still reports a field the landed undo never restored, when someone else now holds it, as a conflict rather than `compensated`.
5. **Never twice.** A patch with a `compensated` or `compensation_conflict` receipt is skipped, and so is one whose undo attempt already settled. An undo sent without a settled outcome (lost response, crash after dispatch) is held, not re-sent blind. A later run reads the ticket. Restored values are recorded only when the undo's private marker is on the ticket; the same values written by someone else are not `compensated`. A stamp that never moved means the undo never landed. That attempt stays open, so the patch stays held and a dependent of it stays recovery-only: a negative read never replays or sends it. Compensation sends a fresh undo once the attempt is old enough, and closes the old attempt only in that same step, after the fresh one is dispatched. A cancelled run, a case that no longer failed, or a send that never starts leaves the attempt open and does not adopt the patch as confirmed. A read that can't tell leaves the hold in place and writes nothing. An undo prepared but never sent had no effect, so a fresh attempt supersedes it. So does an undo refused without a receipt (a crash between 409 rounds), since the refusal wrote nothing. A field the landed undo did not restore, which still holds our value, is reverted by a follow-up; one a teammate changed is a conflict.
6. **The compensation receipt is final.** Once compensation records a result for a patch (`compensated`, `compensation_conflict` or `held`), later runs of that hash reuse it. Another revision copies that receipt once, pointing at the undo attempt. A patch with an undo sent but not settled is held as `unresolved_outcome` until a read settles it; that hold is not final. A patch with any sent undo is never adopted as `confirmed`. An action already sent (confirmed, or with a lost response to reconcile by a read) keeps its own record even if a patch it depends on was undone since; it is never relabelled `skipped_dependency`. That exception is recovery-only: a read that finds the earlier send records it as `confirmed`, but a negative read never permits a replay or a new send, because idempotency stops a duplicate, not a send that the undone patch no longer supports. The lost send is held as `unresolved_outcome` and stays in flight, so a late landing is still found (#99). A refused attempt wrote nothing, so it is still skipped, and so is a dependent whose predecessor is held for any other reason.
7. **Same admission as any send.** No undo is sent after a cancel or once the grant is revoked, changed or expired. The patch gets an `approval_invalid` hold saying our value is still there.

## Consequences

- A refused refund also reverts its case's priority patch, since the remedy didn't happen.
- An empty before value (priority `null`) can't be written back through the typed patch, so that field is held for a manual undo.
- A lost undo response is reconciled by reading the ticket on a later run. The undo carries a private marker. Restored values count only when that marker is present; the same values written by someone else are not `compensated` and are not re-sent. A read that shows the undo never landed can send a fresh one once the attempt is old enough. The old attempt is closed only once that fresh undo is dispatched, so a run that does not send it does not call the patch confirmed. While it is open, a dependent already sent stays recovery-only (#99). The read itself is fixture evidence; the Era gate does not lose an undo response.
- Zendesk's `updated_stamp` has a documented 1-second limit, so an edit within the same second as our re-read may not 409. The receipt says so.
