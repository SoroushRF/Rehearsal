# T4.13 gate: isolation and recovery, end to end

Status: **specified, not run.** The gate can't pass until its blockers land (see [What's missing](#whats-missing)). This page fixes what "pass" means now, so each blocker's owner knows what the gate will ask of their piece, and no one can claim the feature from its parts' tests alone.

Issue: [#175](https://github.com/SoroushRF/Rehearsal/issues/175). Design: [decision 0013](../decisions/0013-execution-rehearsal.md). Feeds [T1.28](https://github.com/SoroushRF/Rehearsal/issues/176).

## What the gate is

One recorded session against a single commit of `main`, on the real stack: the API with Postgres, the rehearsal worker, the executor worker, the rehearsal Era containers plus the planning and operational worlds (`pnpm infra:up:rehearsal`), and the review UI in a browser. Every check below goes through the public API or the UI, the way a reviewer would. A check that calls a package function directly is a component test, not the gate.

The existing component tests (listed under each check) still have to pass on that commit. They don't count as the gate.

## Checks

### G1. The happy path keeps the plan and the shared worlds intact

Request a rehearsal of a stored, hashed plan → disposable worlds → independent report → review display.

Pass when:
- The rehearsal names the source plan's ID, revision and hash. They're unchanged after the run, and the API refuses to start one for a hash that isn't stored.
- The report the UI shows is the verifier's account of provider reads (T4.12), not the executor's receipt labels, and it labels its evidence.
- After the run the planning and operational worlds read back exactly as they did before (same snapshot as `evals/providers/test/snapshot-seed.test.ts` takes), and no `step_attempts`, receipts or grants exist for the plan.
- Teardown removes the rehearsal's `rh-` tenants.

Already proven in parts: `evals/providers/test/rehearsal-run.test.ts` (runner, exact plan, untouched planning world), `snapshot-seed.test.ts` (seed, two rehearsals apart, teardown), `apps/executor-worker/test/rehearsal-mechanics.test.ts` (no grant, own keys).

### G2. Isolation refusals

Each attempt is refused with a recorded reason, and nothing is written anywhere:
- A rehearsal of another org's plan, or a reference to another org's rehearsal (looks like not found).
- A rehearsal routed to a planning or operational world, or to another rehearsal's tenant.
- A source plan whose stored hash no longer matches its content, or a baseline snapshot that doesn't match the plan's evidence.
- Using anything from a rehearsal for operational apply: its approval or grant, its journal rows or receipts, its report. Apply still takes only a stored plan reference with the expected revision and hash, and needs an operational grant for that exact hash.
- After a rehearsal, applying the same plan still runs every operational guard against live state. If the rehearsal led to a revision, the revision needs a new approval.

Already proven in parts: `rehearsal-mechanics.test.ts` (world, tenant and hash refusals; operational admission closed to rehearsal worlds; neither mode adopts the other's history), `apps/api/test/rehearsal-tokens.test.ts` and `evals/providers/test/rehearsal-credentials.test.ts` (tokens and URLs), `rehearsal-run.test.ts` (incompatible baseline, foreign tenants).

### G3. Recovery and honest reports

Run through the API and UI, with the T4.11 challenges where they apply. Each must end in a report that says what happened, including partial and unknown outcomes:

| Scenario | Pass when |
|---|---|
| Phantom charge after the snapshot | The affected step is held with `row_changed` or `query_membership_changed`, its dependents are skipped, and other customers proceed |
| Teammate edit on an owned field | Compensation keeps the teammate's value and records a conflict |
| Benign control (an edit that shouldn't hold) | Nothing is held; the report shows it as a control that passed |
| Lost response | Resolved through reads inside the rehearsal; no second effect |
| Worker killed mid-run, then restarted | The journal is recovered through reads; no request is sent twice; the run finishes or reports unknown |
| Cancellation mid-run | No new sends; in-flight sends are reconciled read-only; the report says partial, naming what's unresolved |
| Precedent withdrawn after planning | The step citing it is held with the precedent reason, and the report and UI show which precedent and why |

Already proven in parts: `rehearsal-mechanics.test.ts` (lost send, cancel stops new sends, unresolved stays unresolved, compensation under its own keys), `evals/providers/test/phantom.test.ts` and `compensation.test.ts` (operational guards on Era). Precedent invalidation at admission: [#258](https://github.com/SoroushRF/Rehearsal/pull/258), open.

### G4. The record

The gate's result is written down in the track file's handoff log and on #175, with:
- the exact commit SHA of `main` and the Era image digests from `infra/compose.yaml`;
- each command run, in order, and which env files each process had (no secrets);
- for each check G1–G3, pass, fail or not run, with the receipt, report or screenshot that shows it;
- the supported scope: which ops, which vendors, the Era seed and state; and what's out of scope, such as native Stripe or real customers;
- the evidence level: `era_integration` only for what ran on the pinned images in this session. Anything else stays `fixture`.

A failed or skipped check means the gate didn't pass. Fix it or narrow the claim; don't relabel it.

## How it will run

Once the pieces land: an operator script next to `scripts/smoke/apply-e2e.ts` drives G1, G2 and G3 through the API, and a Playwright spec under `apps/web/e2e/` checks what the review UI shows for G1 and G3. Both read `ERA_REHEARSAL=1` and `DB_TESTS` like the existing suites, and refuse to run against shared tenants. They're written against the T2.19 API, so they wait for it rather than guess its shape.
